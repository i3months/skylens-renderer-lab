# 0060 T16.0 부하 시험 계약(시나리오·결과 형식)

- 상태: 제안
- 날짜: 2026-10-06
- 결정한 사람: 작업자(제안)
- 관련: TASKS T16.0·T16.6·T16.7, SPEC S8, FEEDBACK F-515·F-516·F-518, 제품 contracts/load/, contracts/metrics/, experiments/t16-0.md, 선례 결정 0034·0036

## 맥락
T16.1~T16.10 서브에이전트가 같은 시나리오·결과 형식에 기대어 병렬로 만든다. 형식을 바꿀 때 기준이 필요하다.

## 선택지와 결정
| 항목 | 선택지 | 결정 | 근거·대가 |
|---|---|---|---|
| 시나리오 종류 | 2종(burst·slow_link) / 3종(steady 추가) | 3종. steady 는 T16.1·T16.4·T16.5 의 기준 부하(30명 일정 경로)로 TASKS 에 이름만 없던 종류다 | burst·slow_link 는 변형이라 기준 시나리오가 따로 있어야 비교된다. 대가: 종류 하나 더 검증 |
| 접속 수 상한 | 30 고정 / 상한 없음 / 목표와 분리 | MAX_CLIENTS = 30 (SPEC S8 목표와 같다) | 30 초과 여유 시험은 이 계약으로 표현하지 못한다. 필요해지면 상한만 올린다(다른 필드 영향 없음) |
| 경로 | 자유 형식 / ENU 웨이포인트 | {t,e,n,u}[]: GeoAnchor 기준 ENU, 1 unit = 1 m, t 초. path[0].t = 0, t 는 엄격 증가, 마지막 t ≤ durationS. 마지막 점 이후는 시나리오가 끝날 때까지 마지막 위치에 머문다 | renderer_basis 의 좌표 규약과 같다. 경로가 시간 밖이면 모의 클라이언트가 해석할 규칙이 없다 |
| burstLevels | 개수 / 수준 번호 | 한꺼번에 도착하는 수준의 개수, 1..LEVEL_COUNT(4, contracts/asset) | 4수준 규약에 묶는다. 번호로 쓰면 어느 수준인지가 따로 필요하다 |
| linkBytesPerS | — | 모의 회선 대역(바이트/초), 양의 유한수 | T16.7 역압 시험 입력 |
| 결과 | 새 스키마 / metrics 재사용 | records 는 contracts/metrics 기록 그대로, perClient[] 는 {id, bytes, latencyMs[]}. id 는 0..clients-1 정수·중복 없음, bytes 는 0 이상 정수(바이트), latencyMs 는 0 이상 유한수(밀리초)·길이 ≥ 1(요청→수신 지연 표본) | T01 스키마 재사용. 길이·id 검사로 '30개 각각 기록'(T16.3)을 한 클라이언트 반복으로 채우지 못한다 |
| 알 수 없는 필드 | 허용 / 거부 | 거부 | 오타가 조용히 무시되는 것을 막는다 |
| 필수 metric 이름 | 계약에서 강제 / 이후 | 이후(T16.8·T16.9 가 SPEC S1~S7 판정용 이름을 정한다). 이 계약은 records 가 비어 있지 않고 metrics 스키마를 만족하는지만 본다 | 이름은 보고서·문턱 파일이 소비하는 쪽에서 정하는 것이 맞다 |

## 대가
- 계약이 의미 검사를 하므로 시나리오 파일 작성자가 경계(끝 t = durationS 등)를 지켜야 한다.
- 합성 검증이며 실제 서버 부하에서 검증한 값이 아니다 [cloud].

## 다시 볼 조건
- 30명을 넘는 시험이 필요해질 때(MAX_CLIENTS).
- T16.8·T16.9 가 필수 metric 이름을 정할 때(계약에 반영할지).
- 수준 수(LEVEL_COUNT)가 바뀔 때.
