# 0039 hook 간격 시험은 벽시계 상한(GAP_LIMIT_MS 60, 최솟값 기준)을 쓴다

- 상태: 승인
- 날짜: 2026-10-04
- 결정한 사람: 작업자(제안)
- 관련: FEEDBACK F-261, 결정 0038, 실험 노트 experiments/t12t.md

## 맥락
결정 0038 은 GL 경계 hook(onGlUploadStart/End, onDrawStart/End)의 위치를 hook_order 시험으로 고정했다. 그러나 hook 과 첫/마지막 GL 호출 사이에 호출 없는 CPU 작업(busy loop 등)을 넣는 변이는 사건 순서만 보는 그 시험을 통과한다(F-261). 호출 없는 작업은 Proxy 로 기록할 수 없고 제품 코드가 그 구간에서 now 를 부르지도 않아 가짜 시계로도 잡을 수 없다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 간격 단언 없음(0038 그대로) | 비결정성 없음 | 경계 안으로 비-GL 작업이 숨는 변이를 못 잡는다 |
| B. 시험이 찍는 실시각 간격에 넉넉한 상한(채택) | 변이를 잡는다 | 벽시계라 이론상 비결정적 |
| C. 제품 코드에 시계 주입 지점을 더 넣어 결정적으로 판정 | 결정적 | 해당 구간에 호출이 없어 넣을 지점이 없다. 제품 코드를 시험용으로 바꾸게 된다 |

## 결정
client/raster/hook_gap.test.mjs 가 (Start→첫 GL 호출), (마지막 GL 호출→End), (onDrawStart→첫 GL 호출), (마지막 GL 호출→onDrawEnd) 간격을 같은 시나리오 REPEAT(5)번 돌려 간격별 최솟값이 GAP_LIMIT_MS(60 ms) 이하임을 단언한다. 이 시험의 벽시계 사용을 허용하며, 결정 0038 의 (f) 허용은 이 결정이 대체한다.

## 근거
- 결정적 대안이 없다(선택지 C 는 넣을 지점이 없다).
- 정상 간격은 수 µs~수백 µs 라 상한 60 ms 는 수백 배 여유다. 변이는 120 ms 를 넣어 상한의 두 배다.
- 최솟값 기준이라 한 번의 GC·스케줄링 지연은 판정에 영향이 없다. 변이는 매번 120 ms 이상이므로 최솟값도 120 ms 이상이다.
- 실측: 원본 10회 0 실패, 변이 3종(Start–upload 사이, makeRoom 앞으로 옮긴 Start 뒤, onDrawStart 뒤 각 120 ms) 실패(experiments/t12t.md).

## 대가
- 비결정성: 벽시계 시험이라 극단적으로 느린 실행기에서는 이론상 거짓 실패가 가능하다(최솟값 기준과 수백 배 여유로 줄였다).
- makeRoom 첫 줄 형태 의존: 짝 시험 hook_order_novictim 은 희생 없는 makeRoom 의 첫 줄 meta.get 을 사건으로 기록해 Start 앞임을 단언하므로, 그 줄의 모양이 바뀌면 시험을 함께 고쳐야 한다.

## 다시 볼 조건
CI 에서 이 시험의 거짓 실패가 1회라도 나면 상한·반복 횟수를 올리거나 결정적 판정으로 바꾸는 방법을 다시 검토한다.
