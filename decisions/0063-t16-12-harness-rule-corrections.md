## 맥락
0062 는 승인되었으나 (2)(5)의 서술이 구현과 달랐고, 마지막 tS 규칙과 first_frame 규칙이 실제 시계·추월 경로와 충돌했다. RULES 에 따라 0062 는 고치지 않고 이 문서가 정정한다.

## 감독 검토(2026-10-06, PR #99 검토 #1)
- 승인(조건부). (A) 마지막 tS ±0.25·ceil 개수·첫 tS 규칙, (B) 섞이면 'mixed' 위반·보고서 'unknown'·loadReport durationS 전달, (C) 어느 수준이든 도착 뒤 first_frame 인정, (E) 다시 볼 조건을 감독이 구현과 대조해 확인했다(감독 재현: tS +0.004·+0.05 → 위반 0, 61개 → 위반, 빈 배열 durationS 60 → 개수 위반, connect@0·level1@500·first_frame@500 → p95 500·위반 0, 도착 전 first_frame → 위반).
- 조건: (A)행은 개수 검사를 실시계 표본 아래에 두었지만 구현은 durationS 가 있으면 모든 시계에 개수를 검사한다(F-562) — 이 행을 고치지 않고 추가 절로 정정한다. (D)의 '또는' 조건부 서술은 '유지'로 확정하고 근거를 적는다(F-563 ⑤). (A) 0.25 s 는 측정값이 아니라 이른 쪽 값을 재사용한 추정임을 밝히거나 T16.12 실시계 측정값을 적는다(F-563 ⑥).
- 이 결정은 하네스 규칙이며 SPEC §4 성공 기준 수치를 바꾸지 않는다(축 5 확인).

## 추가 절 (T16.12 본 작업 정정, F-562·F-563 ⑤⑥)
- (A) 개수 범위 정정: 개수 검사(count = ceil(durationS))는 durationS 가 유한한 양수이면 모든 시계(빈 배열 포함)에 적용된다. 실시계 한정은 타이밍 검사(첫 tS·마지막 tS·간격)뿐이다. durationS 가 유한한 양수가 아니면 위반이다. 위 (A)행 서술은 이 절로 대체한다. 정본은 bench/load/server_stats/index.mjs.
- (D) 피크 칸: '유지'로 확정한다. 근거: 1 s 칸으로 바꾸면 피크가 평균보다 작아질 수 있어 피크로 쓸 수 없다. 짧은 마지막 칸이 피크를 지배하는 것(10 B 가 5 ms 칸이면 2000 B/s)은 알고 둔다.
- (A) 0.25 s: 이른 쪽 값을 재사용한 값이며 측정은 없다(추정). 소켓 부하 1회(10 s, 결정 0064)에서 마지막 tS 는 durationS + 0.0085 s 였다. 한 번 값이라 근거로 삼지 않는다.
