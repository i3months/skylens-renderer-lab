# T02.6 점·가우시안 스플랫 압축 포맷 선행 사례

범위: 조사 문서(코드 아님). 소유 파일 이 하나. 수치는 아래 출처에서 확인한 것만 적고, 확인하지 못한 것은 '미확인'으로 둔다. "우리 추정"이라고 표시한 줄은 출처가 아니라 이 노트의 계산이다.

## 0. 우리 쪽 조건 (적합성 판단 기준)

- 점 형식: 점당 27 B = 위치 float32×3(12) + 법선 float32×3(12) + 색 uint8×3(3). 구간(구역) 하나 정밀본 약 250만 점 ≈ 67 MB (renderer_basis §7-4).
- SPEC §4 대역폭 제안값: 초기 ≤ 15 MB, 구간당(4수준 전체) ≤ 3 MB. 현재 구간당 약 67 MB. 클라이언트 3D 번들 ≤ 300 KB(압축 후).
- 구조: 구간 × 수준(4수준: 딜레이 패턴 250/1,000/3,500/7,000 스텝). 새 수준은 같은 구간의 낮은 수준을 교체(누적 금지), 추월당한 수준은 건너뜀. 따라서 수준별로 독립 디코드되는 조각이어야 한다.
- 우리 점은 가우시안이 아니라 법선이 있는 색 점(점 스플랫/서펠 계열)이다. 가우시안 스플랫 포맷은 스케일·회전·불투명도·SH 필드가 있어 그대로 쓰기보다 양자화 방식만 참고하는 것이 맞다.
- 라이선스 규칙: AGPL·GPL 은 열람만, 코드 차용 금지.

## 1. 사례별 조사

### 1-1. Draco (Google)
- 라이선스: Apache-2.0. 사용 가능.
- 양자화: 속성별 비트 수 지정. 기본값은 위치 11비트, 법선 8비트, 텍스처 좌표 10비트, 색 8비트이며 0이면 양자화 끔. 압축 수준 0~10.
- 점군: `-point_cloud` 로 점군 인코딩 지원. v1.3.0에서 kD-tree 기반 점군 인코딩이 개선되었고 임의 개수 속성을 지원. 문서는 점이 촘촘할수록 압축이 훨씬 잘 된다고 적는다.
- 압축률·복원 오차: 점군 압축률 수치는 이 조사에서 출처로 확인하지 못함 → 미확인(메시에서 v1.3.0 개선이 최대 10%, 평균 약 2%라는 서술만 확인). 복원 오차는 양자화 비트 수가 정한다(위치 11비트면 바운딩 박스 한 변의 1/2048 격자).
- 브라우저 디코드: WASM 디코더 제공. v1.3.6 에서 크기 약 20% 감소, v1.4.0 에서 npm 모듈이 WASM 으로 바뀌며 성능 약 200% 향상(릴리스 노트). 번들 바이트 수와 점당 디코드 시간은 미확인(측정 필요).
- 적합성: 색·법선 속성을 가진 점군을 바로 받는다. 단 kD-tree 방식은 점 순서를 바꾸므로 수준별 조각 단위로 따로 인코딩해야 하고, 수준 간 점진 정제(낮은 수준 위에 쌓기)는 지원하지 않는다. 우리 구조는 '교체'이므로 오히려 맞는다. 디코더 번들이 300 KB 예산에 들어가는지는 측정 전.
- 출처: https://github.com/google/draco

### 1-2. SPZ (Niantic Labs)
- 라이선스: MIT. 사용 가능.
- 압축률: 저장소 문서가 "PLY 보다 보통 약 10배 작고 시각 차이는 최소"라고 적는다. 정량 오차(PSNR 등)는 미확인.
- 양자화: 위치 24비트 고정소수(파일별 fractionalBits), 스케일 8비트 로그, 회전 10비트(버전 3+), 알파 8비트, 색 채널당 8비트, SH 1차 5비트·2차 이상 4비트(1~8비트 조절). 버전 4 는 32바이트 평문 헤더 + ZSTD, 속성 스트림을 독립 병렬 압축.
- 브라우저 디코드: 번들·디코드 시간 수치 미확인. (Spark 등 뷰어가 .spz 읽기를 지원한다는 점만 확인.)
- 적합성: 필드 구성이 가우시안용이라 법선 필드가 없다. 위치 24비트 고정소수 + 색 8비트 + 속성별 독립 스트림 구조는 우리 점에 그대로 응용 가능한 설계 참고. 파일 단위가 한 덩어리이므로 구간×수준마다 파일 하나를 두면 교체 구조와 맞는다.
- 출처: https://github.com/nianticlabs/spz

### 1-3. .ksplat / .splat (GaussianSplats3D)
- 라이선스: MIT. 단 저장소는 더 이상 활발히 개발되지 않으며 관리자가 Spark 를 후속으로 권한다.
- 양자화: compressionLevel 0/1/2. 1 은 스케일·회전·위치·SH 를 32비트에서 16비트로, 2 는 SH 를 8비트로 추가 축소. 압축률 수치는 미확인(정수 비트 절반에서 유추되는 약 2배는 우리 추정이며 출처 없음).
- 브라우저 디코드: GPU 쪽에서 반정밀도로 읽는 구조로 보이나 번들·시간 수치 미확인. 수용 한계는 SH 0차 약 1,600만 개 등으로 명시.
- 적합성: 압축률이 낮아(비트 수만 줄임, 엔트로피 코딩 없음) S6 의 구간당 3 MB 에는 부족할 가능성이 크다. 비트 절삭만으로 가는 최소 구현의 기준선으로만 의미.
- 출처: https://github.com/mkkellogg/GaussianSplats3D

### 1-4. SOG / Compressed PLY (PlayCanvas, SplatTransform)
- 라이선스: SplatTransform MIT. 포맷 문서는 developer.playcanvas.com 이 이 환경에서 차단되어 직접 열람하지 못했다.
- 구조: SOG 는 무손실 WebP 텍스처 여러 장 + 메타데이터 파일. 무손실 WebP 노력 수준 0~9 지원. Compressed PLY 도 읽고 자동 감지. 청크 스트리밍 처리로 1억 가우시안 초과도 변환 가능(변환기 쪽 설명).
- 압축률·복원 오차: 정량 수치 미확인(세부 양자화 비트·k-means 팔레트 여부는 이 조사에서 직접 확인하지 못함).
- 브라우저 디코드: 이미지 디코더를 브라우저가 이미 제공하므로 자체 디코더 바이트가 작을 수 있다는 점은 구조상의 추정이며 수치 미확인.
- 적합성: 점을 2D 격자(텍스처)에 담는 방식이라 구간×수준당 이미지 묶음 하나로 교체하기 쉽고 GPU 업로드가 쉽다. 반면 점 순서를 격자에 맞춰 정렬(공간 상관 유지)해야 압축이 나오고, 법선 추가 시 채널 설계가 필요하다.
- 출처: https://github.com/playcanvas/splat-transform

### 1-5. glTF KHR_gaussian_splatting (Khronos) 와 압축 확장
- 상태: 비준 완료(Khronos 문서 표기). 가우시안을 glTF 메시 프리미티브(POINTS)로 담고 속성으로 위치·회전·스케일·불투명도·SH 0차(필수)를 둔다. 압축은 기본 확장을 확장하는 별도 확장이 담당하며 디코드 결과가 기본 형식과 같아야 한다고 명시. 구현체: CesiumJS, Cesium Native 등.
- 라이선스: Khronos 규격 저작권. 구현하려면 Khronos Adopter 절차(상표·특허 허여)가 얽힌다. 상표를 쓰지 않는 한 영향 정도는 법무 확인 필요 → 사람 확인.
- 압축률·오차·번들: 확장 자체는 형식 규격이므로 수치 없음. SPZ 압축 확장은 이 조사에서 세부 확인 못함(미확인).
- 적합성: 컨테이너·타일링(3D Tiles) 쪽 표준 정렬에는 유리하나 우리 점은 가우시안이 아니므로 현 시점에는 참고만. T02.7(타일링)과 같이 보아야 한다.
- 출처: https://github.com/KhronosGroup/glTF/tree/main/extensions/2.0/Khronos/KHR_gaussian_splatting

### 1-6. Potree / LAZ
- 라이선스: Potree 본체 라이선스는 이 조사에서 확인 못함(BSD 계열로 알려졌으나 출처 미확보 → 미확인). 사용 전 LICENSE 파일 확인 필요. LAZ 디코드는 plas.io 에서 가져온 코드를 쓴다고 문서에 적힘.
- 구조: 다중 해상도 옥트리. 변환기(PotreeConverter)가 점군을 웹 전송용으로 미리 가공하고 정적 서버에 올리면 된다. 최대 180억 점 사례를 문서가 제시.
- 압축률·오차·디코드 비용: 수치 미확인(LAZ 는 무손실 계열이라 위치 오차는 LAS 정수 스케일 격자로 정해짐).
- 적합성: 구조 철학이 우리와 가장 가깝다. 노드(옥트리 셀)=조각, 깊이=LOD 수준, 정적 파일 서빙. 다만 4개 고정 수준 교체보다 일반적인 뷰 의존 노드 선택이다. 법선 필드는 LAS 표준에 없어 추가 속성 필요.
- 출처: https://github.com/potree/potree

### 1-7. MPEG G-PCC (TMC13)
- 라이선스: 저장소에 COPYING 파일이 있다는 것만 확인, 조건 내용은 미확인. 표준 특허 문제가 있을 수 있어 사람 확인 필요.
- 방식: 옥트리·예측 기반 기하 코딩, RAHT 속성 변환, 프레임 내/간 예측.
- 압축률·오차: 출처 문서에 수치 없음 → 미확인.
- 브라우저 디코드: 참조 구현은 C++ 인코더/디코더 통합 바이너리. 브라우저 실행·번들 수치 미확인(WASM 이식 여부도 미확인).
- 적합성: 압축 효율 상한을 보는 기준으로는 유용하나, 디코드가 무겁고 브라우저 이식이 불확실해 300 KB 번들·저지연 교체에 부적합할 가능성이 높다. 서버 측 비교 기준선 정도.
- 출처: https://github.com/MPEGGroup/mpeg-pcc-tmc13

## 3. 우리 추정 (출처 없음, 측정으로 검증 필요)

- 직접 양자화만 쓰는 최소 형식: 위치 uint16×3 (바운딩 박스 격자) + 법선 팔면체 16비트 + 색 3 = 약 11 B/점이면 27 B 대비 약 2.5배 축소. 구간 정밀본 2.5백만 점이면 약 27 MB. 4수준 합계 3 MB 목표에는 점 수를 줄이는 LOD(점 개수 감소)가 주된 수단이고 압축은 보조.
- 점당 약 3 B 에 가까워지려면 SPZ·Draco 식의 엔트로피 코딩과 공간 정렬 델타가 필요. 이 값은 목표 계산용이며 달성 여부 미확인.
- 먼 곳은 깊이 해상도가 d² 로 나빠지므로(SPEC) 먼 점의 양자화 비트를 낮추는 거리 의존 양자화는 오차 예산상 정당하다.

## 4. 잠정 의견

27 B 점은 법선과 위치가 float32 라 양자화만으로도 큰 여유가 있고, 구간당 3 MB 예산은 압축 포맷보다 수준별 점 수 감축(LOD)이 좌우한다고 본다. 따라서 1차 후보는 (a) 우리 필드에 맞춘 자체 소형 양자화 형식(위치 격자 정수·법선 팔면체·색 8비트 + 구간×수준당 독립 조각 + zstd 또는 브라우저 내장 압축)이고, 이는 SPZ 의 속성별 독립 스트림·고정소수 위치 설계를 참고한다. (b) 엔트로피 이득이 더 필요하면 Draco(Apache-2.0)를 수준별 조각에 적용하는 방안을 비교하되, WASM 디코더 크기가 300 KB 번들 예산을 넘는지 먼저 측정한다. .ksplat 은 압축이 약하고 유지보수가 끝나 기각, G-PCC 는 브라우저 디코드 부담으로 기준선 용도, KHR_gaussian_splatting 은 가우시안 전용이라 현재는 보류하되 타일링(T02.7) 결정과 함께 재검토한다. 확정 전 측정 항목: 실제 구역 점군으로 각 방식의 크기·복원 오차·브라우저 디코드 시간·디코더 바이트.
