## 1. 앱의 좌표 규약 (코드 확인)

- `src/shared/viewer/sources/sceneSource.ts:342-356`: 주석에 "our OWN demo capture is baked upright (y-up, ground level) by level_scene.py, so it loads with NO rotation". 즉 앱 규약은 **+y 가 위**이고, 자체 캡처는 회전 없이 그린다.
- 회전 없음(`UP_PRESETS.none`)이 적용되는 것은 `url === CONFIG.splat.demoPreview` 일 때뿐이다. `config.ts:107` 에서 `demoPreview = '/res/static/demo/step00250_light.ply'`. 그 밖의 URL 은 `x180`(antimatter15 규약) 이 붙는다. `?up=` 로 수동 덮어쓰기, `?level=on` 으로 PCA 자동 수평이 가능하나 기본값은 아니다.
- 앱이 직접 여는 것은 step00250_light 이다. 기준 영상이 그리는 step07000_light 는 앱 경로로 직접 열리지 않지만, 아래 3절처럼 step00250_light 와 **같은 회전 하나**로 구워져 같은 틀에 있다.

## 2. 측정 방법 (재현)

스크립트는 저장소 밖 임시 디렉터리에 두었다(저장소에 넣지 않음). 실행:

```
cd <임시 디렉터리>
D=<skylens develop 체크아웃>/res/static/demo
uv run --no-project --with numpy python measure.py \
  $D/step07000_light.ply $D/step00250_light.ply $D/step01000_light.ply $D/step03500_light.ply \
  $D/orig/step07000_light.ply $D/orig/step00250_light.ply $D/step30000_final.ply
uv run --no-project --with numpy python check2.py $D
```

`measure.py` 요지:
- PLY 헤더를 읽어 `element vertex` 개수와 `property` 이름·형식(float→`<f4`)으로 numpy 구조체 dtype 을 만들고 본문을 `np.frombuffer` 로 읽는다. 회전·변환 없이 원시 x, y, z 를 쓴다.
- **방식 B (level_scene.py `measure_up` 과 같은 정의)**: x, y, z 각 축 1~99 분위 상자 안의 점만 남긴 "핵심" 에서, y 의 1·99 분위 a, b 를 다시 구해 세 등분(t=(b−a)/3). 아래 1/3 = `a ≤ y < a+t`, 위 1/3 = `b−t < y ≤ b` 의 비율(분모는 핵심 점 전체).
- **방식 A (y 축만)**: y 의 1~99 분위 안 점만 남겨 같은 세 등분, 아래/가운데/위 비율(합 100 %).
- 핵심 공분산의 최소 고유값 축(지면 법선 후보)과 y 축 사이 각도, y 분위(1,5,10,25,50,75,90,95,99), y 10구간 히스토그램.

`check2.py` 요지:
- orig/step07000 → step07000 의 점 대응(같은 순서·개수)으로 원점 기준 Kabsch(SVD) 회전 R 을 구하고, 실제로 구울 때 쓴 up = Rᵀ·(0,1,0) 을 원래 틀에서 복원. `measure_up` 의 자동 부호(조밀한 1/3 을 아래로)와 비교.
- step07000 의 y 1~99 분위 범위 r 기준, 범위 밖 0.25r·0.5r·1.0r 넘는 꼬리 점 수(아래/위).
- step30000_final(미터 틀)에서 `people.json` 사람 위치 (x, z)=(12.8, 17.84) 주변 반경 1 m·2 m 기둥의 y 분포.

### 3.3 구울 때 부호는 일부러 자동값의 반대로 정해졌다

- 복원한 회전: det = 1.0, 대응점 최대 잔차 4.8e-7 (step07000), 1.8e-6 (step00250). 두 파일 모두 같은 up = (−0.0108, 0.1152, −0.9933) 로 구워졌다.
- 원래 틀 최소분산축 (0.0108, −0.1152, 0.9933) 을 따라 낮은 쪽 1/3 48.5 %, 높은 쪽 1/3 17.7 % → `measure_up` 자동 부호는 (0.0108, −0.1152, 0.9933). **실제로 쓴 up 과 내적 −1.0** — 자동값의 정반대다.
- 커밋 `a9130af` 메시지: "the densest sheet the leveling heuristic reads as ground is actually the canopy in this nadir capture, so the sign must be forced (--up)". `align_scene.py:104-111` 도움말도 같은 이유(나디르 촬영은 지면보다 수관을 더 잘 복원해 부호를 틀린다)를 적었다. `level_scene.py:40-61` 의 docstring("조밀한 쪽이 아래")은 자동 모드 설명일 뿐이며 이 자산에는 `--up` 으로 덮어쓰였다. 따라서 "조밀한 층이 위" 는 의도된 결과다.

### 3.4 지면 위치의 독립 근거

- `people.json` (운영자 확인, "y는 그 지점 바닥 높이") 사람 위치 y = −9.9 m. 최종 자산 전체 y 에서 하위 10.5 % 지점이다.
- 그 사람 주변 기둥(반경 1 m, 5,619점) y 분위 1/10/50/90/99 = −11.37 / −10.57 / −7.25 / −3.99 / −2.56 m. 바닥(−9.9 m) 아래에는 18.5 % 만 있고, 나머지는 바닥보다 위(최대 약 7 m 위까지)에 있다. 반경 2 m 도 같은 모양(18.1 %). 즉 **바닥이 아래, 그 위로 수관·지붕 층** — +y 위 규약과 맞는다.
- 반대 방향 신호도 하나 있다: step07000 에서 1~99 분위 범위 밖 꼬리 점이 아래쪽에 더 많다(0.25r 밖: 아래 1,749 / 위 188, 1.0r 밖: 아래 282 / 위 5). 나디르 촬영에서 떠다니는 점은 보통 카메라 쪽(위)에 생긴다고 보면 반대 신호지만, 반사·무늬 없는 면의 깊이 오류로 지면 아래에 생기는 점일 수도 있어 판정 근거로 쓰지 않았다.

## 4. 판정

1. **앱과 같은 방향(회전 없음)임: 확인.** 앱은 step00250_light 를 `UP_PRESETS.none` 으로 그리고(sceneSource.ts:342-356, config.ts:107), 기준 영상도 회전 none 이다. step07000_light 는 step00250_light 와 같은 회전(같은 up 벡터, 잔차 ≤ 1.8e-6)으로 구워진 같은 틀이므로, 기준 영상은 앱이 보는 방향과 같다.
2. **앱 자산 자체가 뒤집혔는가: 뒤집히지 않았을 가능성이 높으나 확정은 아님.**
   - 위가 조밀한 분포(step07000 위 1/3 49.2 %, 아래 1/3 17.4 %)는 자산 작성자가 "나디르 촬영에서 조밀한 층은 수관" 이라 보고 `--up` 으로 부호를 일부러 뒤집은 결과다(3.3).
   - 운영자가 확인한 바닥 높이(사람 위치)가 하위 10.5 % 에 있고, 그 기둥에서 대부분의 점이 바닥보다 위에 있다(3.4). 이는 +y 위 규약과 맞는다.
   - 다만 사람 위치는 같은 자산 위에서 `?pick=on` 으로 찍은 값이라 완전히 독립된 근거는 아니며, 떠다니는 점 꼬리는 반대 신호다. 렌더 화면을 사람이 눈으로 보아 땅·지붕을 확인한 기록은 이번에 찾지 못했다.

## 5. ② 앱 로더 실제 s·P 대조 — [local] 브라우저 실측 필요

이번 작업에서는 대조하지 못했다. 이유:

- 앱은 `.ply` 를 `SplatLoader.loadFromURL(url, onProgress, false, undefined, 1, 0, true)` (sceneSource.ts:298-306, `@mkkellogg/gaussian-splats-3d` ^0.4.7) 로 읽어 `SplatBuffer` 로 바꾼 뒤 `getSplatCenter` 로 표본을 뽑는다. 이 변환은 최소 알파(1/255) 미만 점을 버리고(`minimumAlpha=1`), `optimizeSplatData=true` 로 점 순서·구간을 다시 짠다. 표본 간격이 `floor(total/60000)` 이고 순서에 의존하므로, 점 수나 순서가 바뀌면 표본 집합과 분위(그래서 s·P)가 이식본과 달라질 수 있다. 참고로 알파 1/255 미만 점은 step00250_light 에 1/8,434개, step07000_light 에 45/465,523개 있다(이번 측정).
- 현재 1e-6 비교(ref_images.test.mjs:251-297)는 이식본끼리의 비교라 이 로더 경로를 거치지 않는다.
- 로더는 fetch·Worker·three.js 를 쓰는 브라우저용이고, 이 작업 환경에는 브라우저가 없으며 skylens 체크아웃에 node_modules 도 없다. 앱이 실제로 쓴 값을 보려면 앱을 띄워 그 값 자체를 받아야 한다.

[local] 실측 절차(안):
1. skylens develop `59edcf9` 에서 `npm ci && npm run dev`, 브라우저로 `?splat=demo` 접속.
2. `deriveFromSplat` 끝에서 구한 `s`, `P`(그리고 `total`, 표본 수)를 콘솔로 찍는다(임시 로그, 커밋하지 않음).
3. 같은 step00250_light.ply 로 이식본이 낸 s·P (보강 측정값 s=5.442149081, P=[−8.851, 2.325, −1.751]) 와 비교해 차 ≤ 1e-6 인지, 아니면 차이와 원인(알파 제거 점 수, 순서 재배치에 따른 표본 차이 등)을 이 노트에 기록한다.
