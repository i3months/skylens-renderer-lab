# T15.3b F-408 ⑦ 건물 층 성능 (결과 버퍼 재사용 + 묶음 컬링)

## 바꾼 것 (client/tower/buildings/)
- `render(camera, out?)`: out 을 주면 지우고(color 0, depth 0, index −1) 같은 객체를 돌려준다. 크기·형식이 다르면 RangeError. 주지 않으면 이전처럼 새로 만든다. render 경로에는 합성 보조 버퍼가 없다(합성은 `composeLayers`). `composeLayers(base, over, into?)` 에 선택 인자 `into` 를 추가해 합성 결과 버퍼도 재사용할 수 있게 했다(.buffer 를 공유하는 배열이면 던진다(into 의 세 배열끼리 포함)).
- 묶음 컬링: accept 때 묶음별 ENU 경계상자(정점·선 끝점·표본점 전부)를 한 번 계산한다. render 에서 모서리 8개를 카메라 공간으로 옮겨 근·좌·우·상·하 평면 중 하나의 바깥에 8개가 전부 있으면 뺀다(가장자리 2 화소 여유, 보수적). 빠진 자리에는 빈 묶음(공유 상수)을 넣어 래스터에 넘기므로 `out.index` 의 묶음 번호는 그대로다. 래스터 파일은 건드리지 않았다.
- 시험·진단용 추가: 생성 옵션 `cull:false`(컬링 끄기), `layer.stats()` → `{groupsTotal, groupsDrawn}`. 계약(buildings.mjs)에 render 의 out 재사용 정의를 추가했다. composeLayers 의 into 는 계약 contracts/controlview/buildings.mjs:34(compose 항목)에 이미 `composeLayers(base, over, into?)` 로 올라 있고 같은 정의(새 typed array 할당 0, 호출 간 재사용)를 따른다.
- 유한성: `validate.mjs` 가 positions·edgeLines·points 를 accept 때 이미 검사한다. index.mjs 의 render 경로에는 정점별 isFinite 가 없다(추가하지 않았다). 래스터 안의 정점별 검사는 그대로다(아래 한계).

## 측정 [cloud] (1280×720, 3000동, 100묶음, 7회 중앙값(시험 reuse_cull.test.mjs·perf.test.mjs 와 같은 방식, 예열 2회 뒤) 을 3번 반복한 값의 중앙값 [범위: 최소–최대], CI 컨테이너 CPU, node)
장면은 `reuse_cull.test.mjs` 의 합성 도시(60×50 격자, 동 간격 50 m, 6×5동씩 묶음). 전 = HEAD 의 index.mjs(매 프레임 새 버퍼, 컬링 없음), 후 = 이번 변경(out 재사용 + 컬링). 이번에 다시 잰 전은 같은 코드에서 `cull:false` + out 없이 호출한 값(옛 HEAD index.mjs 를 다시 돌린 것은 아니다). 실행마다 흔들림이 커서 3회의 범위를 함께 적는다.

|---|---|---|---|

| black | 900 m 확대(면적 1/10) | 27.6 [23.2–34.9] | 16.4 [15.6–21.0] |
| black | 비스듬(800,−1500,400) | 60.5 [50.0–79.8] | 79.6 [64.5–81.4] |

도시 전체(컬링이 못 빼는 장면)는 black 후가 전보다 오히려 느리거나 같고(32.8 대 27.8, 범위가 겹침), aerial 도 후 26.2 대 전 21.4 로 개선이 아니다. 전체·비스듬 시점의 차이는 잡음(범위 겹침) 안이며, 이득은 컬링이 묶음을 빼는 1/10·확대 장면에서만 보인다.

시험 ③ 은 black 도시 전체 대 1/10(묶음 12/100 ≤ 33)을 단언한다(≤ 1/3). 이번 측정에서 후 black 은 도시 전체 약 21~35 ms 대 1/10 약 3.1~3.4 ms. 컬링 효과는 묶음 분할(서버 묶음 크기)에 달렸고 perf.test.mjs 합성 번들은 이 측정 당시 1묶음이라 컬링 무효였다(1묶음 edge 시점 켬 11.4 대 끔 9.4 ms). 현재 perf.test.mjs 의 GROUP_COUNT 는 6 이다(F-417 ③, t15-3e.md).

## S1(33 ms)과의 관계
- 도시 전체를 보는 black/aerial 은 실행마다 약 21~35 ms(이번 3회 후 값, reuse_cull 장면), S1 의 33 ms 를 자주 넘고 비스듬 시점은 reuse_cull 장면 약 65~81 ms, perf.test 장면(5회 중앙값, 3번 실행)은 그 측정 당시 1묶음이라 black 35~72 ms·aerial 27~72 ms 였다. 현재 perf.test.mjs 는 6묶음이고 수치는 t15-3e.md 표(black 최대 64 ms·전체 최대 70 ms)이다(CPU 경로, 실기기는 [local]). 여유는 없고 CPU 잡음이 변경 효과보다 크다. 비스듬 black 은 후(79.6)가 전(60.5)보다 나쁘게 나왔으나 범위가 겹쳐 개선도 악화도 단정하지 못한다. 과제에 적힌 41~112 ms 는 이 장면에서 일부(비스듬)만 재현된다. 묶음 컬링은 서버가 건물을 공간 타일로 묶어 줄 때만 효과가 있다(공간 묶음 구성은 이 작업 밖, 서버/자산 쪽 확인 필요).
- 컬링은 화면 밖 묶음의 삼각형·선 준비 비용을 없앨 뿐 화소 채우기 비용은 줄이지 않는다. 가까이 확대한 장면(900 m)은 후 black 16 ms·aerial 26 ms(범위 15~41)로 채우기가 지배하며 컬링 이득이 작다(black 27.6 → 16.4, aerial 29.5 → 26.5 는 컬링 + 버퍼 재사용 합이고 aerial 은 범위가 겹친다).

## 한계·보고
- black 모드의 `lines.mjs` lineMark(약 0.9 MB)는 통합 단계에서 모듈 수준 재사용 버퍼로 바꿨다(호출마다 fill(0)). 시험 ① 의 ArrayBuffer 증가 단언은 points·aerial 에만 있고 black 은 out 의 `===` 만 본다 — black 의 ArrayBuffer 단언은 미추가.
- 입력 유한성 검사는 래스터에 따로 있다: points.mjs:36(표본점 x·y·z), lines.mjs:82(edgeLines 끝점), raster_flat.mjs:127(정점 월드 좌표). accept 의 validate.mjs:27 과 겹치는 방어이므로 래스터 단독 호출용으로 남겨 둔다(제거 여부는 소유자 몫, 안 고침). 반면 points.mjs:40·lines.mjs:67 의 `Number.isFinite(d)` 는 입력 검사가 아니라 `Math.fround` 한 깊이가 float32 유한 범위를 넘는지 보는 검사(넘으면 그리지 않음)이며 validate 와 중복이 아니다.
- lines.mjs 는 선분마다 작은 배열(`pq`)을 만든다(GC 압력). 같은 소유자 몫.
- 컬링은 묶음 경계상자 단위라 한 묶음이 도시 전체를 덮으면 못 뺀다.
- 남은 병목은 raster_flat rasterSub 64.6%(비스듬 black 이번 측정 reuse_cull 장면 65~81 ms)로 T17 [local] 성능 판단 때 다룬다.
- 실기기 fps 는 [local]. 위 ms 는 CI 컨테이너 CPU 값이다.
