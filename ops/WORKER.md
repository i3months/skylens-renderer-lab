# 작업자 절차

작업자는 TASKS·FEEDBACK 을 제품 코드와 실험 노트로 옮긴다. 자동 주기로 돌며, 한 실행은 한 검토 단위에 도달하면 끝난다.
먼저 [RULES.md](../RULES.md) 와 [SPEC.md](../SPEC.md) 를 읽는다.

## 0. 시작 점검 (매 실행 맨 처음)

1. 연구 main 의 `STATUS.md` 를 읽는다. **상태가 `진행 중` 이고 `마지막 갱신` 이 8분 이내면 즉시 종료한다**(다른 작업자가 돌고 있다). 아무것도 쓰지 않는다.
2. 상태가 `대기` 로 시작하면 사람이 시작을 허락하기 전이다. 즉시 종료한다. 사람이 `시작 허락` 으로 바꾼 뒤부터 일한다.
3. 두 저장소를 최신으로 받고 클론마다 설정한다:
   ```
   git config user.name i3months
   git config user.email waysoleward01@naver.com
   git config core.hooksPath .githooks
   ```
4. STATUS 를 `진행 중` 으로 바꾸고 `마지막 갱신` 에 지금 시각(UTC)을 적어 연구 main 에 바로 커밋·푸시한다. 이후 10분을 넘기지 않게 갱신한다.

## 1. 무엇을 할지

1. STATUS `감독 지시` 를 먼저 따른다.
2. 그다음 FEEDBACK 의 열린 항목(치명 → 높음 → 중간 → 낮음).
3. 그다음 TASKS 의 다음 미완 작업. 자동 주기 세션은 **[cloud] 만** 한다. [local] 은 건너뛰고 STATUS `다음 할 일` 에 남긴다.
4. 제품 PR 에 감독 댓글이 있으면(라벨이 떼어진 PR) 그것이 그 작업의 다음 일이다.

## 1.1 결정 기록

기술적 결정이 필요하면 구현하기 전에 `decisions/NNNN-이름.md` 를 `상태: 제안` 으로 쓴다(형식은 decisions/README.md). 선택지 비교, 측정값과 출처, 대가, 다시 볼 조건을 적고 실험 노트를 링크한다. 결정 기록이 빠진 PR 은 반려된다.

## 2. 병렬 구현 — 서브에이전트 10개 이상

[cloud] 작업 하나를 다음 순서로 한다.

1. **계약 먼저.** 하위 작업 `.0`(인터페이스·타입·자산 포맷·테스트 픽스처·빈 테스트 이름)을 작업자 본인이 제품 `feat/<작업>` 에 직접 커밋·푸시한다.
2. **분배.** 남은 하위 작업(10개 이상)을 서브에이전트에게 하나씩 맡긴다. 동시에 띄운다.
   - 각 서브에이전트는 **격리된 작업 트리**(자기 브랜치, 계약 커밋 위)에서 일한다.
   - 지시문에 다음을 반드시 넣는다: 하위 작업 번호, **소유 경로**(이 경로 밖은 만들지도 고치지도 않는다), 계약 위치, 완료 기준(돌릴 테스트와 통과 수치), RULES §4~§6(라이선스·비밀정보·흔적 금지), "푸시·PR·댓글·라벨 금지", "계약을 고쳐야 하면 고치지 말고 보고".
   - 작업 트리를 만들 때마다 그 안에서 `git config user.name i3months`, `user.email waysoleward01@naver.com`, `core.hooksPath .githooks` 를 설정하게 한다(설정이 빠지면 다른 신원으로 커밋이 남는다). 푸시 전 `git log --format=%an` 으로 신원을 확인한다.
   - 소유 경로는 서로 겹치지 않는다. 공용 파일(빌드 설정·의존성 목록·CI·README)은 작업자만 고친다.
3. **통합은 작업자 본인이 한다.** 서브에이전트 결과를 `feat/<작업>` 에 하나씩 병합하고, 소유 경로 밖 변경이 있으면 버린다.
4. **검증도 본인이 한다.** 전체 빌드·린트·테스트를 돌리고 하위 작업별 완료 기준 수치를 직접 확인한다. 서브에이전트의 "통과" 보고만 믿지 않는다.
5. 서브에이전트가 실패하면 같은 하위 작업을 다시 맡기거나 본인이 마무리한다. 실패를 숨기지 않고 실험 노트에 적는다.

[local] 작업과 문서 작업(T02 등)도 같은 원칙(소유 경로 분리·본인 통합)을 따른다.

## 3. 명령 (T02 확정, SPEC §8)

| 용도 | 명령 |
|---|---|
| 형식 검사 | 아직 없음(도구를 들이면 여기 적는다) |
| 린트 | 아직 없음(도구를 들이면 여기 적는다) |
| 단위 테스트 | 제품 저장소에서 `npm test` (Node 22, `node --test`) |
| 헤드리스 클라이언트 테스트 | 기설치 Playwright Chromium(SwiftShader WebGL2). 명령은 T12 계약에서 확정 |
| 번들 크기 검사 | T12 전까지 esbuild `--bundle --minify --format=esm` + gzip -9 근사 기록만(문턱 아님, 결정 0009 Q9) |
| 벤치 | `bench/` 아래 도구별 명령(T01 노트 참조). 문턱 비교는 `bench/thresholds/` 생기면 기재 |

확정 전 작업(T01·T02)은 실험 노트에 실제로 쓴 명령을 적는다.

## 4. 브랜치와 PR

- 제품: `feat/<작업>` → base 제품 `main`. 제품 main 에 직접 푸시하지 않는다.
- 연구: `experiment/<작업>` → base 는 **부모 `experiment/*` 또는 `research`**. main 으로 병합하지 않는다. 실험 노트 `experiments/<작업>.md` 를 여기에 쓴다.
- 연구 main 의 STATUS·TASKS(체크 제외)·FEEDBACK(처리 표시)는 main 에 직접 커밋한다. TASKS 체크와 FEEDBACK 닫기는 감독만 한다.
- PR 제목·본문은 한국어, 커밋 메시지는 영어. 본문에 하위 작업별 완료 기준 수치, 새 의존성(이름·버전·라이선스), 차용 코드(출처·라이선스), renderer_basis 이탈과 이유, README 변경 여부를 적는다.
- 올리기 전에 제목·본문에 생성 도구 흔적이 없는지 직접 확인한다(훅은 PR 본문을 보지 못한다).

## 5. 검토 요청 — 이벤트 핸드오프

1. 검토 단위(하위 작업 전부 통합·검증 완료, 또는 FEEDBACK 항목 처리 완료)에 도달하면 제품 PR 에 **`review-requested` 라벨을 붙인다.**
2. STATUS 에 `검토 요청: <작업> (제품 PR #n, 연구 PR #m)` 을 적고 `진행 중` 을 `검토 대기` 로 바꿔 커밋·푸시한다.
3. **종료한다.** 라벨을 붙인 뒤 같은 실행에서 더 일하지 않는다.
4. 작업자는 PR 에 **댓글을 달지 않는다.** 전할 말은 PR 본문 갱신이나 STATUS 로 한다.

GitHub 조작 수단(첫 실행 점검 결과, 자세한 것은 STATUS `환경` 절):
- `gh` 의 GraphQL 명령(`gh pr list`·`gh pr edit` 등)은 이 환경에서 막힌다. **REST 인 `gh api` 를 쓴다.**
  - 라벨 붙이기: `gh api repos/i3months/skylens-renderer/issues/<n>/labels -f 'labels[]=review-requested'`
- **PR 을 만든 직후 본문을 다시 읽는다.** 환경의 GitHub 경로가 PR 본문 끝에 생성 도구 문구를 자동으로 덧붙인다. 붙어 있으면 GitHub 도구의 PR 갱신(`update_pull_request`, body 지정)으로 원래 본문을 다시 써서 지우고, 다시 읽어 확인한다. `gh api` PATCH 로 고치면 문구가 다시 붙는다.

## 6. STATUS 쓰기

```
- 상태: 대기 | 시작 허락 | 진행 중 | 검토 대기 | 회귀 주기
- 현재 작업:
- 마지막 갱신: YYYY-MM-DDTHH:MMZ
- 검토 요청:
- 방금 한 일:
- 다음 할 일:
- 막힌 점:
- 감독 지시: (감독만 쓴다)
```

## 7. 회귀 주기

감독이 STATUS 를 `회귀 주기` 로 바꾸면 개발을 멈춘다. 작업자는 감독 지시나 FEEDBACK 이 있을 때만 그 항목을 고친다. 새 기능을 임의로 만들지 않는다.

## 8. 하지 않는 것

- 테스트를 건너뛰거나 끄거나 기준을 낮추기.
- 훅 우회(`--no-verify`), 남의 브랜치 이력 다시 쓰기, 빈 커밋으로 CI 다시 돌리기.
- 비밀정보(서버 주소·계정·포트·자격증명·API 키)를 어디에든 쓰기.
- AGPL·GPL 계열 코드 차용(먼저 감독에게).
- 컴포넌트 경계·전송 규약 변경(먼저 감독에게).
