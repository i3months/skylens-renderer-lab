# 감독 절차

감독은 작업자의 결과를 직접 검증하고, 병합하거나 고칠 것을 남긴다. 자동 주기 실행과 라벨 이벤트로 돈다.
먼저 [RULES.md](../RULES.md) 와 [SPEC.md](../SPEC.md) 를 읽는다.

## 0. 시작 점검

1. 두 저장소를 최신으로 받고 클론마다 설정한다:
   ```
   git config user.name i3months
   git config user.email waysoleward01@naver.com
   git config core.hooksPath .githooks
   ```
2. STATUS·FEEDBACK·TASKS·지난 감독 기록(`logs/supervisor/<날짜>.md`)을 읽는다.
3. STATUS 가 `대기` 이면 사람의 SPEC 확인 전이다. 감독 기록 한 줄만 남기고 끝낸다.

## 1. 무엇을 볼지

1. 제품 저장소에서 **`review-requested` 라벨이 붙은 PR** 을 찾는다. 이것이 검토 대상이다.
2. 라벨 붙은 PR 이 없으면: 작업자 진척(최근 커밋·STATUS 시각)만 기록하고, 필요하면 main 의 정밀 검토로 FEEDBACK 을 보강한다.
3. **[local] 결과**(사람이 띄운 세션의 실측)는 실험 노트의 수치·명령·기기 정보를 확인한다. 감독 세션은 GPU 가 없으므로 [local] 수치는 재현 대신 기록 일관성을 본다. 단, 성공 기준 최종 판정(§6)은 사람이 띄운 감독 세션이 직접 재현한다.

## 2. 검증 — 서브에이전트 12개 축 병렬

검토 대상 PR 하나에 대해 서브에이전트 12개를 동시에 띄운다. 모두 **읽기 전용**이다(커밋·푸시·댓글·라벨 금지). 각자 한 축만 보고 발견을 심각도(치명/높음/중간/낮음)·위치·실패 상황·확인 기준으로 돌려준다.

| 축 | 본다 |
|---|---|
| 1 정확성 | 투영·역투영·K 환산·좌표 변환이 renderer_basis §2·§1-2 와 일치하는지 |
| 2 계약 | 계약(`contracts/`·`format/`)과 구현·테스트가 일치하는지, 소유 경로 밖 변경이 있는지 |
| 3 테스트 품질 | 정답과 비교하는지, 항상 참인 단언·자기 비교·건너뛰기·기준 완화가 없는지 |
| 4 완료 기준 | TASKS 의 하위 작업별 수치를 실제로 돌려 재현하는지 |
| 5 딜레이 패턴 | 4수준 교체·누적 금지·추월 건너뛰기·타이머 진행 금지 |
| 6 도착한 것만 | 메우기·보간·가짜 표면·시뮬레이션이 없는지, "없음" 표시 |
| 7 좌표계 | GeoAnchor ENU, 1 unit = 1 m, skylens `geo.ts` 와 1 mm 이내 |
| 8 성능·예산 | 대역폭·메모리·번들 예산, 성능 회귀(이전 벤치 대비) |
| 9 경계·전송 | COMPONENTS 경계, 웹소켓 단일 규약 위반 여부 |
| 10 라이선스 | 차용 코드 머리 고지, 새 의존성 트리의 AGPL·GPL, OpenMVS 코드·주석 유입 |
| 11 비밀정보·흔적 | 주소·계정·포트·자격증명·키, 생성 도구 흔적(커밋·PR·주석·문서) |
| 12 문서 정합성 | 제품 README 한·영 일치, 실험 노트 수치 = 테스트 단언, SPEC·TASKS 와 어긋남 |

- **치명·높음 발견은 감독이 직접 확인한 뒤에만 채택한다**(테스트를 직접 돌리거나 코드를 직접 읽어 재현). 재현 못 하면 기각하고 기록에 이유를 적는다.
- 중간·낮음은 근거가 분명하면 채택한다.
- 감독 본인은 전체 빌드·린트·테스트를 직접 돌린다(명령은 §7).

## 3. 결정과 핸드오프

검토 대상 PR 하나마다 둘 중 하나:

- **병합**: 채택된 치명·높음이 0 이고 완료 기준이 재현되면 제품 PR 을 병합하고, 짝 연구 PR 을 부모(`experiment/*` 또는 `research`)로 병합한다. TASKS 에 체크·날짜·제품 커밋을 적는다. 라벨을 뗀다.
- **반려**: PR 에 **댓글 하나**를 달고(채택된 발견 요약과 FEEDBACK 항목 번호) 라벨을 뗀다. 상세는 FEEDBACK 에 쓴다.

규칙:
- 감독은 **실행당 PR 하나에 댓글 한 번만** 단다.
- 감독은 라벨을 **붙이지 않는다**(떼기만 한다).
- 실험 노드는 main 으로 병합하지 않는다.
- 댓글·FEEDBACK 에 생성 도구 흔적을 넣지 않는다.

## 3.1 결정 기록 점검

- 이번 PR 에 기술적 결정(언어·라이브러리·포맷·알고리즘·SPEC 수치·기각)이 들어 있는데 `decisions/` 에 기록이 없거나 근거·대가·다시 볼 조건이 빠졌으면 **높음**으로 FEEDBACK 에 올린다.
- 작업자가 `상태: 제안` 으로 올린 결정은 검토 때 `승인` 또는 `기각` 으로 바꾸고, 승인·기각 근거를 그 파일에 덧붙인다. 목록 표(decisions/README.md)도 갱신한다.
- 감독이 직접 내린 결정(범위 쪼개기, 모델 배정 기준 변경, 성공 기준 해석 등)도 같은 형식으로 남긴다.

## 4. FEEDBACK 쓰기

```
### F-001 [열림|처리됨-검증대기|닫힘] (심각도: 치명/높음/중간/낮음) — 한 줄 요약
- 위치: 경로:줄 (브랜치/커밋)
- 문제:
- 실패 상황: 구체적 입력 → 잘못된 출력/패닉/잘못 통과하는 테스트
- 고칠 것:
- 확인 기준: 감독이 돌려서 닫을 수 있는 테스트·수치
- 이력: YYYY-MM-DD HH:MM 감독 등록 → … 작업자 처리(커밋) → … 감독 확인 닫음
```

- 닫는 것은 감독만, 확인 기준을 직접 돌려 통과했을 때만.
- 같은 문제가 다시 생기면 새 번호 대신 기존 항목을 다시 연다. 닫힌 항목은 지우지 않는다.

## 5. 감독 기록

`logs/supervisor/<YYYY-MM-DD>.md` 에 실행마다 한 절:

```
## HH:MM UTC
- 작업자 상태: (근거: 마지막 커밋·STATUS 시각)
- 진척:
- 검증: 돌린 명령과 결과 수치
- 병합: / 반려:
- 피드백: 신규 n건, 닫음 n건, 열림 n건(치명 n·높음 n)
- 정리: 저장소 분리 위반 n건, 비밀정보·흔적 n건
- 지시: (STATUS 감독 지시에 쓴 내용)
- 전체 진척: TASKS 완료 n/N
```

STATUS 의 `감독 지시` 는 감독만 쓴다.

## 6. 종료 조건과 회귀 주기

- SPEC §4 성공 기준을 **전부** 통과하고 감독이 **직접 재현**하면 개발 주기를 끝낸다. 최종 재현은 [local] 이 필요하므로 사람이 띄운 감독 세션에서 한다.
- STATUS 를 `회귀 주기` 로 바꾼다. 이후 감독은:
  - 테스트 재실행(전체),
  - 성능 회귀 감시(벤치를 `bench/thresholds/` 문턱과 비교),
  - 문서 정합성(README 한·영, SPEC·TASKS·실험 노트)
  만 본다. 회귀가 나오면 FEEDBACK 에 올린다.
- 새 기능을 임의로 만들지 않고, 작업자에게 새 기능을 지시하지 않는다. 2단계 시작 같은 범위 확장은 사람이 정한다.

GitHub 조작 수단(PR 목록·라벨 떼기·병합·댓글)은 STATUS `환경` 절의 첫 실행 점검 결과를 따른다.
- `gh` 의 GraphQL 명령은 막힌다. `gh api`(REST) 또는 GitHub 도구를 쓴다.
  - 라벨 붙은 PR: `gh api 'repos/i3months/skylens-renderer/issues?labels=review-requested&state=open'`
  - 라벨 떼기: `gh api -X DELETE repos/i3months/skylens-renderer/issues/<n>/labels/review-requested`
- **댓글을 단 직후 본문을 다시 읽는다.** 환경이 생성 도구 문구를 덧붙이면 GitHub 도구의 댓글 수정으로 지우고 다시 확인한다. 이 수정은 "댓글 한 번" 에 포함된 같은 댓글의 정정이다.

## 8. 라이선스 검토

클린룸은 적용하지 않는다. 웹 검색·열람은 허용한다. 감독이 보는 것은 **가져온 코드**다.
- three.js, GaussianSplats3D(MIT): 차용 가능, 파일 머리 고지 확인.
- OpenMVS(AGPL-3.0): 열람만. 코드·주석이 들어왔으면 치명.
- 그 밖 AGPL·GPL 계열: 차용 금지. 들어왔으면 치명, 사람에게 올린다.
- 차용 코드는 파일 머리에 출처·라이선스가 있어야 한다. 없으면 높음.
